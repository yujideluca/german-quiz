# pipeline-check and revisao-manutencao: design

Status: DRAFT, waiting for Giovanni's approval. Nothing is built yet.

## Intent and why
Today the quality gate is strong, but it holds only because Claude remembers to run it. Mature teams make the
machine refuse the merge. This project adds two pieces that talk to each other through one file, `report.json`:

- **`pipeline-check`**: a program that measures and blocks. Deterministic, runs in CI without Claude.
- **`revisao-manutencao`**: a skill that judges and proposes. Only Claude runs it.

Basis: ISO/IEC/IEEE 14764 (maintenance types), Lehman's laws, evolutionary architecture (fitness functions),
DORA metrics (see `~/dev/project-template/docs/MAINTENANCE.md`).

## Goals
- G1 A violation of the architecture rule fails the CI build and blocks the merge.
- G2 A fitness function at 85 % of its limit shows a warning (aviso) and does not fail; at 100 % it fails.
- G3 The skill reads `report.json` and produces prioritised `debt` issues and a Preventive decision-log row without measuring anything itself.
- G4 First applied to QuizApp; only afterwards copied to the other projects and to `project-template`.

## Non-goals and anti-goals
- The program never judges (priorities, "is the ADR right?"); the skill never measures by hand.
- Neither closes issues, changes a limit, promotes a version or changes branch protection without Giovanni.
- No parallel system: it extends `tools/quality_gate.sh`, `tools/fitness_check.py` and `tools/metrics.py`.
- No local Qwen. No third-party personal data in memory.
- Anti-goal: a check that passes because it measures nothing (the current fitness check only greps `build.gradle.kts`).

## Decisions by Giovanni
- Programming language of `pipeline-check`: **Rust** (rule work.ask-language).
- GitHub CLI: Giovanni installs `gh`. GitHub checks are read-only.
- CI gets the binary by compiling it in the CI job with a cargo cache; no binary committed.
- Rust libraries allowed: serde, serde_json, toml, clap. `git` and `gh` are called as processes.
- Changing branch protection is an external action: Claude asks first; the program only reads it.
- The first run of `revisao-manutencao` in a project does a full diagnosis of the code and creates an automated bug-finding test. That test is generated by a **separate skill** (prompt still to come from Giovanni; name and method are open until then). On later runs, when the project already has the test, `revisao-manutencao` checks it and updates it to match what was implemented since.

## Piece 1: `pipeline-check` (Rust)
Input: the repository. Output: `report.json`
`{projeto, data, modo (local|ci), checks:[{id, status: ok|aviso|falha, valor, limite}], dora:{frequencia, lead_time, retrabalho, parcela_preventiva}}`.
Exit code is non-zero if any check is `falha`; `aviso` never fails.

Checks:
- a. project gate passes (runs `tools/quality_gate.sh`).
- b. real architecture test: no `android.*` import or dependency in the pure module (`core/`); a violation fails the build. Scans source imports, not only the Gradle file.
- c. fitness functions: each has a limit in the config; aviso at >= 80 %, falha at >= 100 %.
- d. DORA from git and CI run history.
- e. CI green on the last push; branch protection requires the CI (read-only, via `gh`).

Modes: checks that need the laptop (device, `~/dev` feed, local toolchain) run only in `local`; the report states the mode that ran, and a skipped check is reported as skipped, never as ok.
Config: one TOML file per project (`pipeline-check.toml`) with the limits; limits are decided by Giovanni and changed only in a commit that has an ADR or decision-log row.

## Piece 2: skill `revisao-manutencao`
Trigger: the monthly review (open item #4dcb2c) and the end of a task in a software project.
1. Run `pipeline-check`, read `report.json`; do not re-measure.
2. For every aviso/falha, propose a `debt` issue with priority P1 (risk of data loss or wrong result), P2 (slows every change), P3 (desirable).
3. Check what a machine cannot see: do DESIGN.md and the ADRs match the code; does every structural change have an ADR; was the same problem solved twice in different projects (move the better solution to `project-template`).
4. Record a Preventive row in each reviewed project's decision log.
5. Close with `mem use REF --note`, `wiki publish`, and end with "Verified by:" (what ran, what could not be checked).
6. Bug-finding test: if the project has none, do the full diagnosis and call the separate bug-test skill to create it; if it has one, check it and update it to match the project.
The skill proposes; Giovanni decides.

## Constraints
Never force-push. Ask before any external or destructive action. First debug pass and a real test before saying "done".

## Acceptance criteria
1. Planting an architecture violation makes the CI fail and block (shown on a branch, not merged).
2. A fitness function pushed to 85 % shows AVISO and exit code 0.
3. Given an example `report.json`, the skill yields issues with priority and one Preventive row, with no measuring of its own.
4. QuizApp first; copy to other projects after.

## Traceability
Requirements first (`docs/REQUIREMENTS.md`), tests tagged `REQ <ID>`, then code; ADR "the program measures, the skill judges".

## Calls made after the builder check (Claude's calls, for Giovanni to review)
- C1 Mode split: check e (CI green on the last completed run of the default branch; branch protection requires the CI job) runs in `local` mode only, because inside CI it would be circular and the default token cannot read protection. In `ci` mode it is reported `pulado`.
- C2 Warning threshold: 80 % is the default, configurable per project in the TOML. Acceptance test 2 uses 85 % (above 80, below 100).
- C3 DORA: report-only, no limits, `null` when there is no data. Sources: deployment frequency = beta and stable publishes in the feed (as `metrics.py` does today), lead time = commit to stable release, rework = share of Corrective rows in the decision log, preventive share = share of Preventive rows (target about 20 %, shown as a note, not a failure). Computed from git and the decision log; CI run history only for the CI-green numbers.
- C4 Gate in CI: `pipeline-check` is the single CI job; it runs `quality_gate.sh` once (check a) and reads its duration for the gate-time fitness function. No double run.
- C5 Relation to Python: the Rust program ports `fitness_check.py` (retired in the same commit, CLAUDE.md wording updated) and the DORA part of `metrics.py`; `metrics.py` stays only for the human-readable monthly printout until the Rust report replaces it.
- C6 Check b: any `android.*` or `androidx.*` import in `core/` Kotlin/Java sources, or Android in `core/build.gradle.kts`. The planted violation for acceptance test 1 is a source import in a file that a deliberately broken build setup would let through (e.g. a dependency added), proving the check itself catches it; the compiler is not what is tested.
- C7 Report: status adds a fourth value `pulado` (skipped). A check marked required for the mode that is skipped is `falha`. The report has `schema_version: 1`.
